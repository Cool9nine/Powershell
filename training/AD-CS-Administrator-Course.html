01 · The hierarchy and what each component does

OFFLINE ROOT CA
Trust anchor · signs subordinate CAs · root CRL
↓ signs
ISSUING CA(S)
Additional issuer(s), if deployed
↓ issue
Domain controllers · member servers · authorized users

A certificate binds a name to a public key. The enrolled server or user retains its private key. The issuing CA signs the certificate with a different CA private key. Clients validate name, purpose, time, chain, trust and revocation. The root usually remains off; issuing CAs serve daily requests.

Public itemWhere it goesPurpose
Root certificateTrusted Root store via AD/GPO or an approved distributionTrust anchor; never distribute root private key
Issuing CA certificateIntermediate store/AIA/ADBuild chain to the root; intermediate alone does not establish root trust
Issued certificateSubject’s store and target applicationIts matching private key stays with authorized subject
CRL / OCSPReachable publication endpointsCheck revocation of certificates from the particular issuing CA
Additional online issuers can help with new enrollment. Existing certificates still depend on the original issuer’s chain and revocation endpoints.

02 · Read-only discovery first

Document each issuer separately, plus the root. Record host, CA common name, standalone/enterprise role, root/subordinate status, OS, service state, CA certificate generations and dates, key provider/HSM, CA ACLs, database, backups, enrollment role services, published templates and web endpoints.

For each certificate generation record AIA and CDP locations embedded in certificates already issued, not only current registry settings. Inventory root and issuer CRL ThisUpdate/NextUpdate, HTTP replication jobs, delta CRLs, DNS, firewalls and consumers outside the domain.

# On EACH issuing CA (elevated Windows PowerShell):
Get-WindowsFeature ADCS*
Get-Service CertSvc
certutil -cainfo
certutil -ca.cert C:\Temp\ThisCA.cer
certutil -getreg CA
certutil -getreg CA\CRLPublicationURLs
certutil -getreg CA\CACertPublicationURLs
certutil -getreg CA\CRLPeriod
certutil -getreg CA\AuditFilter
Import-Module ADCSAdministration
Get-CATemplate

# Domain-connected administrative workstation:
certutil -config - -ping
certutil -ADCA
certtmpl.msc
pkiview.msc

# Inspect copies of representative certificates and CRLs:
certutil -dump C:\Temp\SampleServer.cer
certutil -verify -urlfetch C:\Temp\SampleServer.cer
certutil -dump C:\Temp\SampleCA.crl

Record which GPO grants computer/user autoenrollment, which templates are issued by each CA, who has Read/Enroll/Autoenroll, and which separate features exist: /certsrv, CEP/CES, NDES/SCEP, OCSP. Examine actual certificate samples from each issuer and old CA key generation.

These commands are discovery. Do not run -setreg, -dspublish, -revoke, remove templates, or renew a CA during inventory.

03 · Trust, AIA, CDP and CRLs

AIA helps retrieve issuer certificates. CDP names locations for CRLs. OCSP, if configured, offers online status. A root’s CRL covers subordinate CA certificates it issued; each issuer’s CRL covers its own end-entity certificates. A certificate already issued retains the URLs embedded when it was issued.

  1. Inspect a certificate’s AIA and CDP with certutil -dump.
  2. From a representative relying client, retrieve every listed HTTP/LDAP location.
  3. Confirm the CRL issuer and ThisUpdate/NextUpdate; compare published copies and expected overlap.
  4. Generate a scheduled new CRL on the correct CA using certutil -crl.
  5. For the offline root, transfer only public .crl and CA .cer files via approved media to each publication location; independently fetch the URLs and validate a chain before shutting the root off.
certutil -crl
certutil -dump C:\Temp\FreshCA.crl
certutil -verify -urlfetch C:\Temp\Sample.cer

Base and delta CRLs can have separate schedules. Keep older CA certificates and CRLs available until dependent certificates have expired. Document the next root power-on date before its CRL expires. Availability must be assessed from Windows, vendor, and off-domain clients that consume the certificates.

Running certutil -crl creates a CRL on the CA; it does not prove that every HTTP mirror has been updated. Some applications cache or skip revocation; test the actual consumer.

04 · Template design and publication

Templates live in the forest configuration partition and define enrollment rights, subject and SAN construction, key provider and size, private-key export, EKUs/application policies, validity, renewal, approval, supersedence and compatible client/template versions. A template must be created in certtmpl.msc and published to each intended enterprise issuing CA.

  1. Specify consuming service, exact DNS/identity names and authentication purpose.
  2. Duplicate an appropriate baseline template; check compatibility with the oldest approved requester.
  3. Set EKU narrowly (for example Server Authentication for a TLS-only service); review requester-supplied SAN/subject carefully.
  4. Choose provider/algorithm, key storage, key size, exportability, validity and renewal. Effective validity cannot outlast the issuer certificate’s remaining validity.
  5. Set Read, Enroll and Autoenroll only for intended principals; review owner, Write and Write DACL.
  6. Consider manager approval and authorized signatures for sensitive identities; inspect enrollment agents.
  7. Publish on the intended CA(s), pilot a single request, inspect the resulting certificate, and test the service.
# On the intended issuing CA:
Import-Module ADCSAdministration
Get-CATemplate
Add-CATemplate -Name "ApprovedTemplateName"

# Stops new issuance after an impact review;
# it does NOT revoke certificates already issued:
Remove-CATemplate -Name "ApprovedTemplateName"
Broad enrollment plus requester-controlled names plus authentication-capable EKUs creates an identity escalation path. Do not assume that removing a template from a CA deletes its AD object or revokes past certificates.

GPO trust distribution installs public root/intermediate material; it does not by itself obtain a server certificate and key. A user’s enrollment and a computer’s enrollment run under different identities. Web Enrollment may omit modern version 3/CNG templates: check MMC or certreq before treating that as a CA outage.

06 · Domain controllers and LDAPS

LDAPS commonly uses TCP 636, global catalog TLS 3269, and StartTLS upgrades LDAP on 389. A DC needs a certificate with a matching DNS name, appropriate Server Authentication use, accessible private key, a trusted chain and usable revocation data. DC/Kerberos templates may have additional PKINIT requirements beyond TLS.

  1. Inspect Cert:\LocalMachine\My and the NTDS service store if used. Note multiple eligible certificates.
  2. Identify the certificate actually presented by the DC, not merely the most recently issued one.
  3. From the LDAP application client, validate DNS, TCP, TLS certificate, trust chain, CRL/OCSP and a real LDAP bind.
  4. After renewal, confirm the presented certificate changed; schedule a controlled service reload or DC restart only if selection requires it.
# On DC:
Get-ChildItem Cert:\LocalMachine\My |
  Select-Object Subject,DnsNameList,Thumbprint,NotAfter,HasPrivateKey
certutil -store My

# Client socket test (NOT a certificate test):
Test-NetConnection dc.example.gov -Port 636

# Full test: ldp.exe → Connection → Connect →
# hostname dc.example.gov, port 636, SSL; then Bind.

Windows clients may trust the root through domain policy while Linux devices or appliances require their own trust bundle. Certificate-based AD logon and strong mapping enforcement are separate from the TLS handshake for LDAPS; review Kerberos authentication before changing DC templates.

08 · Renewals, rollover and transfers

A leaf certificate renewal may create a new private key and does not guarantee that the application switches bindings automatically. CA renewal is more consequential: decide same key versus new key, retain old CA certificate/key generations and associated CRLs, and plan chain publication for old and new leaf certificates.

ChangePreserve/check
Issuing CA renewalRoot signature of new subordinate CA request; issuer identity, old/new chain, validity and CDP/AIA
Root renewalRoot trust distribution, subordinate CA validity, old/new root generations, CRLs and consumer compatibility
CA migrationCA name, key/HSM, database, registry, template assignments and URLs embedded in already-issued certificates; prevent duplicate active CA identities
Service certificate transferProtected PFX with permitted exportable private key, target machine store, key ACL and service binding; prefer fresh enrollment when possible

Exporting a public .cer alone does not transfer the service identity. An ordinary PFX transfer workflow is not a CA private-key migration plan. HSM-backed and nonexportable keys require separate procedures. Back up and rehearse before CA renewal or migration.

09 · Backup and recovery

Protect CA database and logs, CA key/HSM recovery material, every CA certificate generation, registry configuration, CAPolicy.inf if present, publication job configuration, template/ACL inventory, and web/OCSP/NDES dependencies. Keep secured offline copies and rehearse a restoration in isolation.

# On CA: approved secure storage
Import-Module ADCSAdministration
Backup-CARoleService -Path "D:\ApprovedSecureBackup"

# Documented certutil alternative:
certutil -backupdb D:\ApprovedSecureBackup\Database
certutil -backupkey D:\ApprovedSecureBackup\Keys

# Capture configuration separately:
certutil -getreg CA
certutil -getreg CA\CRLPublicationURLs
certutil -getreg CA\CACertPublicationURLs

Key material requires restricted access. Microsoft’s standard backup may not recover an HSM key; follow the HSM vendor’s quorum/recovery process. A CA database without its original key cannot resume issuing as that CA. A key without database and URL configuration is an incomplete recovery.

  1. Record CA identity, key provider and all current/old certificate generations.
  2. Restore in an isolated lab using the supported Microsoft migration procedure.
  3. Verify CertSvc, database, template publication, CRL generation, HTTP/LDAP publication and representative enrollment.
  4. Ensure there are not two active hosts operating the same CA identity.
A VM snapshot alone is not a validated CA recovery strategy.

10 · PKI as an identity security boundary

  • Restrict CA administration, Manage Certificates, template edits, Write DACL/owner, backup keys, enrollment-agent rights and NTAuth publication. Separate administrative roles where feasible.
  • Audit issuance, denied/pending requests, CA and template configuration, role changes, privileged logons and key operations. Confirm both Windows audit policy and the CA audit filter produce expected events.
  • Review templates combining broad enrollment, requester-controlled identity and authentication EKUs. Inspect SAN request-attribute settings and CA-level controls.
  • Harden /certsrv and Certificate Enrollment Web Service: HTTPS, Extended Protection for Authentication, and Microsoft NTLM relay mitigations; disable unneeded role services.
  • Keep CA hosts patched and restrict network paths. Protect publication endpoint write access while maintaining its read availability.
  • For certificate-based AD authentication, validate strong certificate mapping/SID extension behavior; deprecated compatibility bypasses cannot be your long-term plan.

Revoking one abused certificate is not sufficient if a permissive template remains able to mint more. Investigate issuance history and correct the underlying permissions or template design.

12 · Guided change playbooks

Publish a template

Approve purpose and authorized requesters → duplicate baseline → narrow EKU/name/ACL → publish on selected CA(s) → pilot → inspect key/chain/CRL → test consuming service → monitor renewals. Remove CA publication to stop new issuance; decide separately about revoking already-issued certificates.

Onboard an application or appliance

Identify server or client authentication, all names, where key is generated, supported algorithms, CSR route, service binding and renewal owner. Install leaf and needed chain, check CRL access, and test a real client.

Revoke a compromised certificate

Confirm issuer, serial and thumbprint; prepare replacement. Revoke the exact certificate on its issuer with an appropriate reason; publish and fetch fresh revocation data; test the consumer, investigate private-key exposure and record incident evidence.

Operate the offline root

Approve a planned window → validate time/physical access/backup → issue root CRL or sign authorized subordinate request → export public files via approved media → copy to every endpoint → retrieve and verify from clients → document next deadline → power off.

Migrate an issuing CA

Inventory and backup → rehearse restore → isolate old host during cutover → restore CA identity/database/key/configuration on replacement using supported procedure → maintain legacy AIA/CDP URLs → publish CRLs → test enrollment and LDAPS consumers.

13 · Knowledge checks

An issuing CA is online; why would LDAPS still fail?

The DC may present a wrong certificate, the client may lack root/intermediate trust, or the original issuing CA’s CRL/chain endpoint may be broken.

Why does a modern template not appear at /certsrv?

It may be unpublished, denied by ACL, or unsupported by the legacy web enrollment dropdown (notably version 3/CNG).

Does removing a template revoke existing certificates?

No. It stops new issuance on the selected CA; past certificates remain governed by their own lifetimes and revocation.

Is successful TCP 636 proof of valid LDAPS?

No. Establish TLS, validate the presented certificate and perform a real LDAP bind from the client.

Can you move a service certificate using only a .cer file?

No; the matching private key is required. Use a permitted protected PFX workflow or enroll a new certificate on the target.
